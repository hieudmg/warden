## Trust model and deployment

Protect management/data access against network peers, hostile web origins, offline database theft without passkeys/recovery, malicious remote filenames/terminal strings, and unsafe distribution transports. Passkeys do not make arbitrary public exposure safe; network restriction remains optional defense in depth.

Both init and normal service have an explicit HTTPS public origin and stable RP ID. Public origin is one canonical HTTPS scheme/host/port with no userinfo/path/query/fragment; RP ID follows WebAuthn's domain rules and is stored with initialization. Do not derive either from request headers. A changed RP ID/origin fails startup with recovery/re-enrollment guidance, rather than resetting identity. A DNS alias is not an automatically trusted origin.

Two deployment modes use the same public contract:

- Direct TLS: configured certificate/key paths and bind address; verify request Host against configured public authority.
- Same-host trusted reverse proxy: HTTP backend bound only to a literal loopback address; explicit proxy mode, backend authority, and configured public origin. Proxy must enforce HTTPS, preserve the configured public Host (or use the explicitly configured backend authority), reject unexpected hosts, and remove untrusted forwarded headers. Backend uses configured origin, not arbitrary `Forwarded`/`X-Forwarded-*` values; no header can promote a remote request to trusted HTTPS. Same-host processes are within this proxy trust boundary.

`init` prompts for storage/config paths, public origin, RP ID, and direct-TLS or loopback-proxy configuration and validates them before binding. Persist non-secret config privately; never place secrets in env/service units. Defaults must not silently allow public HTTP, even on a private network. CLI public endpoints require HTTPS too; local HTTP is only the configured server-side proxy hop. Document private CA trust, not `InsecureSkipVerify`.

## Initialization state machine

States: **uninitialized -> registration-only -> initialized/locked**; normal runtime is **locked <-> unlocked**. Setup is a separate short-lived process, never a mode toggled through a management route.

1. `warden-server serve` refuses absent/uninitialized or incompatible storage before migrations/writes. `warden-server init` refuses initialized storage and any legacy/unknown nonempty database. It never resets an installation, deletes a DB/key, or overwrites existing state. Lock out concurrent init/serve attempts on the same storage.
2. Bind a validated listener first. On readiness, generate an unbiased random eight-character password from `23456789ABCDEFGHJKLMNPQRSTUVWXYZ` (32 symbols, 40 bits), write it only to the controlling terminal, and start an absolute 15-minute deadline. Refuse to disclose it to redirected stdout/stderr; use an injectable terminal seam for tests. No URL/query, access log, error, audit payload, or browser persistence contains it.
3. The init mux serves only setup HTML/static dependencies and `/api/v1/setup/*`. No management API, CLI API, report, transport, export, generic static override, or normal SPA fallback is mounted. Password submission obtains a short-lived Secure/HttpOnly/SameSite=Strict setup cookie and CSRF token, bounded by the original deadline; it cannot extend that deadline.
4. Globally allow at most 20 wrong password attempts for this init process; rate-limit submissions at one/second with burst five, bound body sizes and concurrent setup ceremonies. Expiry or exhaustion closes the listener and exits. No per-IP-only defense, sliding lifetime, or automatic password rotation while listening. Use generic rejections and constant-time secret comparisons.
5. Register the first owner passkey with required UV, obtain working PRF output, generate/wrap a random data key and recovery key, and require the owner to re-enter the saved recovery key to prove recovery unwrap before completion. Merely checking “saved” is insufficient. Failed/unsupported PRF cannot commit an initialized installation.
6. Finalization consumes the setup authorization exactly once and commits the format marker, owner, credential, passkey wrapper, recovery wrapper/verifier, and data-key check in one transaction. No partial initialized state. Once commit wins, reject every further setup request, close the temporary listener, drain/cancel in-flight setup work, clear transient secrets best-effort, and exit. A crash after commit leaves an initialized locked installation; rerunning init refuses it. A crash before commit permits a fresh explicit init with no committed owner. Config files may remain, but never imply initialization.

No boot-time master-key generation or unauthenticated “unlock with this supplied key” endpoint replaces this flow.

## Authentication, sessions, and route audiences

Keep a small server-owned auth package and persistence tables beside the existing store. Open initialized auth metadata without a vault key. Initially gate **all existing managed-data operations while locked**, even redacted lists; this avoids pretending current getters are key-independent. Locked login/status/security metadata must not use those getters. No need to refactor every list into metadata-only access to achieve the first milestone.

### WebAuthn contract

Use a maintained Go verifier, with required UV, exact RP ID and origin, and explicit server-side expiry enforcement. Challenges are CSPRNG 32-byte values, expire after five minutes (or earlier init deadline), and are stored server-side with owner, session/setup/recovery context, purpose, and intended credential/target. Consume on finish attempt atomically; reject replay, concurrent reuse, wrong purpose, wrong owner/userHandle, unknown/revoked credentials, invalid signature, wrong origin/RP ID, absent UV, expired/mismatched challenge, and cross-origin/embedded ceremonies. Request no identifying attestation policy; no vendor allowlist. Follow verified library semantics for signature counters and synced credentials; do not assume all valid software passkeys have increasing nonzero counters.

PRF output is client-side key material, **not signed proof of identity**. Do not serialize it to the server as part of generic extension outputs. Server verifies the actual WebAuthn ceremony independently before accepting wrapper changes or data-key delivery. Registration followed by an authenticated `get()` is the supported baseline for obtaining PRF output: creation may report PRF capability without results. Successful registration without usable PRF must not create an active vault-unlock credential. Authentication of an existing credential can work while locked without PRF; unlocking cannot.

### Sessions and fresh actions

Opaque CSPRNG 32-byte session tokens; persist only token hashes and server-side owner/expiry/revocation state. Secure, HttpOnly, SameSite=Strict, Path=/ host-only cookie (`__Host-` prefix); rotate on login and recovery authentication. Idle lifetime 30 minutes, absolute lifetime 12 hours, enforced server-side. Browser stores neither session bearer tokens nor vault material in local/session storage, IndexedDB, caches, or URLs. Logout revokes that browser session; it does **not** globally lock the vault. Global lock drops server key access independently of login.

Every management data route under existing `/api/v1/` requires a web session; API credentials cannot substitute. Static login/setup assets contain no management data. Only bounded login/setup/recovery/pairing handshake endpoints are reachable before authentication; none returns managed data. Unknown API paths fail closed, including path aliases/trailing slash/method variations.

Unsafe cookie-authenticated methods require exact configured Origin, session-bound CSRF header, and `application/json`; reject `text/plain`, form, missing/foreign/null Origin. Safe sensitive GETs (key vault/export) also need the action grant described next. Host validation applies before routing, including login/static/errors; no CORS grants to foreign origins. Fetch Metadata adds defense, never replaces Origin/CSRF checks. API bearer requests are not cookie-authenticated and still reject foreign Origin when supplied.

Bound auth challenge state to eight pending ceremonies per session and 128 globally; bound registered passkeys to 32. Rate-limit login starts/finishes globally (five/second, burst ten) and recovery proof failures (one/ten seconds, burst five); return generic 429 with Retry-After and bounded state. Init has its stricter lifetime/failure contract above. Limits must not trust proxy-supplied client addresses or create an unbounded per-IP map.

Fresh verification is a new required-UV WebAuthn assertion, not an age flag on the login session. It yields a server-side single-use grant valid for 60 seconds, bound to owner/session, action, and target/request digest. Require it for enrollment/removal of passkeys, recovery-key generation/replacement, unlock/key delivery, vault key-pair reveal or mutation, export, import, CLI credential approval/revocation, and other key-management operations. Bootstrap and verified recovery have explicitly restricted corresponding grants, not generic bypasses. A grant for one action cannot approve another or be used by another tab/session. Revoke relevant sessions/grants on credential removal/recovery replacement.

## Key custody and cryptographic wire contract

Use a CSPRNG 32-byte random vault data key (DEK), independent of every passkey. The existing AES-256-GCM field codec uses that DEK. Changing a passkey wrapper does not require re-encrypting the database. Server persists only wrappers and an authenticated key-check record, never an unwrapped DEK or locally recoverable fallback.

Version 1 wrapper contract (strict JSON, base64url without padding for binary fields):

- `version: 1`, `kind: "passkey" | "recovery"`, random 16-byte `vault_id`, `credential_id` for passkeys, random 32-byte `kdf_salt`, 12-byte fresh `iv`, and 48-byte `ciphertext` (32-byte DEK plus 16-byte GCM tag). Passkey wrappers additionally store random 32-byte `prf_input`.
- Browser supplies `prf_input` to the standard PRF extension's `eval.first`; WebAuthn performs its specified input domain separation. Do not implement an alternate authenticator protocol or double-apply that transformation. For a selected credential use the stored input; server's ceremony credential binding prevents returning a different credential's wrapper.
- Passkey KEK: HKDF-SHA-256 with PRF `results.first` as input key material, `kdf_salt` as salt, UTF-8 `warden/v1/passkey-wrap` as info; derive a non-extractable AES-256-GCM key for encrypt/decrypt only.
- AAD is UTF-8 compact JSON of the positional array `["warden",1,kind,vault_id,credential_id]`; recovery uses an empty final string. Binary identifiers in this array use their canonical base64url strings. No object-key-order dependence. Enforce lengths/canonical encodings, purpose/version and credential/vault binding; Go/JS shared vectors fix the exact bytes.
- Wrap raw DEK bytes with AES-GCM using that AAD, a new IV per encryption, and 128-bit tag. Reject malformed/truncated/unknown-version envelopes, wrong key/salt/AAD/credential/vault and tampering. Test IV freshness/RNG failure on encryption; do not claim decryption can detect arbitrary historical nonce reuse. Never return a partial plaintext on failure.

The browser authenticates first, then receives only its authorized wrapper, unwraps locally and sends the raw DEK over authenticated HTTPS with its single-use unlock grant. Server validates the DEK using the initialized key-check ciphertext/AAD before enabling it; it does not accept a replacement key because a client supplied one. A stale login or possession of the DEK alone authorizes nothing. Browser clears transient PRF/DEK buffers and drops references after delivery; don't send a KEK or PRF output to the server. A malicious active server could still serve JS that steals those values; this is not zero knowledge.

Keep DEK availability in one runtime vault owner, not copies on each `Store` or handler. Secret operations acquire access from it; locked access returns stable `423 vault_locked` without decryption. Lock stops new access, cancels/drains in-flight secret operations before acknowledging success, and drops key/codec references best-effort; responses already delivered cannot be recalled. Race tests must prove a late operation cannot re-enable or return new secrets after lock acknowledgement. Restart always constructs the runtime locked regardless of persisted sessions. Do not persist a resume/unlock token.

### Additional passkeys and recovery

To add a passkey, the owner must be authenticated, freshly verified, and unlocked. Verify the new registration and its follow-up assertion/PRF before committing. Obtain the same DEK through an action-bound, freshly authorized HTTPS key-delivery operation from the unlocked vault, wrap it with the **new** passkey's KEK, and validate wrapper round-trip before committing the credential/wrapper pair. A new passkey cannot derive the old passkey's KEK or decrypt its wrapper. Deliver no server key to an unverified new credential; bind the old-owner authorization to that pending new credential. Deletion removes its wrapper, revokes sessions/grants issued through it, and refuses to remove the last active passkey until a replacement is committed.

Recovery key: 32 random bytes, displayed as `warden-recovery-v1:` followed by canonical unpadded base64url with a copy/save warning; not a human password. HKDF-SHA-256 derives separate AES wrapping and recovery-authentication subkeys using independent info labels `warden/v1/recovery-wrap` and `warden/v1/recovery-auth` and the recovery wrapper's random salt. Store SHA-256 of the 32-byte authentication subkey, never that subkey or the recovery key. Using independent subkeys prevents the stored verifier from unwrapping the DEK.

Recovery is a narrowly scoped HTTPS protocol: obtain a short-lived nonce/context and public salt, submit the derived authentication subkey over TLS for hash verification and consume that context, then obtain a restricted recovery session. This reusable high-entropy proof is password-equivalent authentication, not a WebAuthn signature or a claim of phishing resistance. Rate-limit it, never log it. Only after this fresh verification return the recovery wrapper and accept DEK delivery against the key check. That session can unlock and authorize replacement-passkey enrollment; it cannot export/read managed data as a general management session. Owner clarification on resumed T3: “remove all passkeys then. and force register new passkey”. Recovery MUST register and verify a new PRF-capable passkey, independently verify its required-UV signed assertion, validate the same DEK against the initialized key check, and confirm a local new-wrapper round-trip. Only then atomically replace ALL old passkeys and wrappers with this one new credential/wrapper and revoke all prior sessions and client authorizations; require ordinary passkey login afterward. Never delete old credentials before this successful atomic replacement: aborted/failed recovery commits no identity change. Normal management is unavailable throughout restricted recovery, even after recovery unlock. Replacement preserves the existing recovery root/wrapper; rotating recovery material is a separate explicit saved-confirmed operation. Until T4 adds durable client records, retain an atomic authorization-generation contract for future client invalidation rather than inventing a client schema. Recovery does not bypass encryption. Rotating recovery material requires fresh passkey verification while unlocked, local round-trip/saved confirmation, and atomic wrapper/verifier replacement; the old recovery key stops working against current state.

## CLI pairing and API credentials

Use a separate explicit `/api/v1/client/` route audience on the configured HTTPS service, sharing handler/store logic, not a second unauthenticated path. Do not distinguish browser/CLI by User-Agent or reachability. Cookie sessions cannot authenticate client routes and bearer API credentials cannot authenticate management/security routes.

Expose only existing CLI capabilities: SSH/DB list/get/dependents and archive operations, SSH/DB transport, project list/create, reports list/create. No export/import, vault key-pair reveal, enrollment, recovery, global unlock, or auth administration through API credentials. Adjust `internal/client/api` and `internal/client/report` paths together. Future capabilities need explicit route inclusion, not a wildcard alias to all management APIs.

First connection without credentials starts pairing, not anonymous data access:

1. The existing per-user local agent generates a 32-byte random API secret in memory and submits its hash with a pairing request over HTTPS. The agent owns that token and makes authenticated API requests on behalf of CLI commands over protected local IPC; do not persist the API token in a file or pass it back to CLI processes. Server allocates a random request ID and a separate 32-byte polling secret (store its hash), expires the request after five minutes, and caps outstanding requests at 20, creation at one/second with burst five, and each request's polling at one/second. Raw API and polling secrets remain in agent memory.
2. CLI displays the configured-origin approval URL, request/device label and credential fingerprint; never API/poll secrets in the URL or terminal. Browser requires passkey login and a fresh approval assertion, shows the same fingerprint, and approves only that pending commitment. Denial/expiry cannot activate it; replay cannot replace its hash.
3. Polling with the polling secret reveals only that request's status. On approval, durably activate the stored API-secret hash/revocation record, surviving server restarts; the agent retains the raw token only in memory. There is no idle/absolute client-token expiry, automatic rotation, refresh token, or disk API credential. Agent exit/restart loses the token and requires new web approval; server restart alone does not require reapproval. The daemon runs until externally terminated: no timed/idle exit at all, even unauthenticated, logged out, revoked, or with an empty SSH pool. SSH graph/pool idle eviction remains allowed but never terminates the daemon or discards an otherwise approved token. Logout clears/revokes authentication without terminating the process; revocation, server outage/restart and vault lock are not daemon-exit triggers. External cancellation must terminate cleanly. Deterministic fake-clock tests must advance past pool TTL and long idle, prove the empty-pool agent remains alive, cover logout/revoke/outage/lock while alive, and verify clean external cancellation. No default credential shared between installations/devices, no token in command arguments/env/logs. An unpaired CLI cannot fetch any managed data.
4. The agent sends bearer credentials only to the exact configured HTTPS origin; individually list/revoke by non-secret ID/label and hash lookup, not plaintext recovery. Check durable revocation on every request, including pooled clients. Global lock gates secret/data routes even for valid API credentials. Private IPC trust/discovery material (including its separate local IPC authentication token and trust certificate) may remain on disk with native permissions/ACL validation; it must never contain the API token. Revocation prevents future retrieval; already retrieved bundles and established client SSH/DB sessions remain a separate local exposure.

Owner-selected residual risk: a stolen API token remains usable until explicit server-side revocation (or installation/recovery invalidation), even after the originating agent exits. Agent exit loses the legitimate process's copy; it does not remotely revoke an exfiltrated copy. This simple model deliberately has no automatic expiry/rotation/refresh-token work.

## Full audit remediation requirements

These remain in release scope after the early runnable authentication/vault milestone. Named tests/task boundaries are in the plan.

### Backend

- Outer Host allowlist and Origin/JSON/CSRF checks must defeat cross-origin `text/plain` POST and DNS rebinding, even through setup, proxy mode and errors.
- Explicit header/read/write/idle deadlines. Initial contract: header 5 s, read 120 s, write 120 s, idle 60 s, 1 MiB ordinary bodies, existing 50 MiB import limit. A representative full-size import must complete on the documented supported link; slow/stalled/oversize clients terminate and cannot extend setup lifetime. Proxy timeouts must cover the same import contract. Bound concurrent expensive requests too.
- Preserve depth 32 but add cumulative graph work/output budget (initial maximum 1,024 expanded node occurrences per resolution, including duplicates) plus context checks. Count work before lookup/recursion, preserve the accepted route's order and duplicate semantics; do not deduplicate away behavior. Validate structural graph using non-secret rows before decrypting passwords/key pairs. Dangling soft references remain importable but fail transport resolution.
- Set no-store before routing all auth/data endpoints: key vault GET, transport, export/import, status and every error including 401/403/404/423/429/500. No conditional-cache secret response. Do not rely on success handlers alone.
- Replace audit raw error strings with allowlisted stable classifications (`validation`, `invalid_json`, `invalid_graph`, `unauthorized`, `locked`, `rate_limited`, `storage`, `internal`, etc.), never supplied validation values/SQL/key material. Cap UA at 512 UTF-8-safe bytes and encoded metadata at 4 KiB with an allowlist and safe truncation/omission. Include actor/credential IDs, never tokens. Classify before truncating; cap source/request metadata without trusting forwarded headers.
- Remove the legacy master-key loader from the normal/init runtime and installer; if any legacy utility still loads it, open first without following unsafe links, validate the opened descriptor's type/owner/mode, and read that descriptor to eliminate the stat/open race. No dormant fallback path.
- Keep row/field AES-GCM AAD and atomic import. Setup auth/wrappers are not managed transfer records; initialized empty vaults can import old data, and import must never replace owner/auth/recovery state.

### Frontend

- Frame denial (`frame-ancestors 'none'` plus X-Frame-Options DENY), nosniff, and a CSP tested against actual production Vite/React/CSS/font assets. Start with default-src 'none'; self script/connect/style/font, no inline scripts/eval, base-uri 'none', object-src 'none', form-action 'self'. Any required inline styles must be evidenced by emitted assets/runtime components and narrowly accommodated; do not blindly enable unsafe scripts. Referrer-Policy no-referrer.
- All managed/auth fetches, including export and errors, use `cache: 'no-store'`, same-origin credentials and appropriate CSRF/action headers. No service-worker or persistent secret caching.
- Default-mask SSH/DB/proxy passwords and secret passphrases; explicit reveal controls reset when closed/locked/logged out. Update old tests that deliberately assert text fields rather than treating them as immutable UX requirements.
- Markdown must not issue external image requests automatically. Render a non-fetching placeholder/link; user activation may open the external image with an explicit privacy warning, not silently expand CSP. Keep HTML disabled and safe link protocols/opener isolation. A test verifies no network request on rendering hostile Markdown.
- Global auth/lock generation invalidates outstanding secret/export/file promises. Abort where possible; generation checks still reject late completions after lock/logout/dialog change/unmount, including export Blob/object URLs and recovery state. Preserve existing key-pair request guards and wipe references/form state best-effort.

### Local IPC, file transfer, SSH lifecycle and output

- Before a Windows agent client transmits runtime token, bundle, command/SQL or stream bytes, authenticate the listening server over a TLS 1.3 protected local channel. At agent startup generate a per-runtime self-signed certificate/private key; retain the private key only in agent memory and publish the exact trust certificate with the existing runtime token in the private runtime credential file. Client trusts only that certificate, verifies its fixed `warden-agent` name and validity, and completes TLS before sending the existing bounded token-authenticated request frames. Do not enable early application data/0-RTT or reuse trust/resumption state across runtimes. Use a dedicated trust pool, not system-root acceptance or skip-verification; bound handshakes and reject stale/wrong-runtime certificates. TLS also protects against a relaying impostor reading payloads; do not invent a custom nonce/MAC/encryption handshake. Secure runtime directory/credential-file ACL and listener ownership too; unpredictable naming alone is insufficient. Bump private IPC/credential-file version coherently with no plaintext fallback; maintain Unix endpoint ownership/stale-socket safety. Native Windows adversarial pipe/ACL tests are required, not cross-compilation alone.
- Reject malicious remote directory entry names before joining to either namespace: empty, dot/parent, separators of either kind, absolute/UNC/drive-qualified/drive-relative names. Verify destination containment under native path rules; do not rely solely on POSIX clean when writing Windows paths.
- Local and SFTP adapters must create exclusive private sibling staging files **before** any content, not `Create` followed by chmod. Fail if safe private creation is unsupported. Handle collisions/symlinks, close/errors/cleanup, then final mode/atomic rename; preserve old target on failure. Private staging must remain private during writes regardless of source final mode.
- SSH_AUTH_SOCK may still authenticate a connection; never implicitly request forwarding. Default forwarding disabled independently of authentication for exec, interactive sessions and pooled graphs. Do not add a new opt-in product feature just to preserve the unsafe default. Close agent connections/forwarding registrations with their owning graph and evict canceled/unusable pooled graphs.
- Preserve existing external DB and HTTP CONNECT proxy transport behavior. No mandatory or optional external TLS feature, TLS profile fields, schema/form plumbing, or transfer-format extension is part of this release. Retain the documented `warden-data` version 1 export/import contract and its soft-reference semantics; this does not imply compatibility with old encrypted databases.
- SSH second-hop dial, SSH handshake, proxy CONNECT (direct or through a hop), and DB channel open must honor cancellation/timeouts even when `SetDeadline` returns unsupported. Close the owned channel/graph to unblock, reclaim late results, avoid leaked goroutines; invalidate a borrowed pooled graph if shared transport must be closed. Do not close unrelated healthy pooled operations silently.
- Escape untrusted terminal API error text and DB column headers in interactive tables as well as TSV; retain cell sanitization. Cover ESC/OSC/C0/C1/DEL and multiline controls. Do not sanitize intentional interactive SSH byte streams or corrupt binary/file streams.

### Distribution, dependencies, CI

- API clients reject cross-origin and HTTPS-to-HTTP redirects **before sending any credential/body**, including injected HTTP clients. Prefer refusing all API redirects; tests exercise hostile custom clients without mutating shared injected configuration. `api.New` must make its own copy of an injected `*http.Client`, override redirect following (refuse all API redirects), and leave the caller's instance unchanged; no separate request path may use the unguarded instance. A post-response origin check is too late.
- Release assets/checksums/installers use HTTPS for original URLs and every redirect, with verified TLS. HTTPS cross-host CDN redirects may be needed for releases; this is different from the no-cross-origin API policy. Injected updater transports must not bypass HTTPS redirect enforcement. Current `Options.HTTPClient Doer` permits arbitrary redirecting `Do`; replace that seam with a controlled `*http.Client` copy/owned redirect loop and transport-level test injection, not an unconstrained production Doer. Check each Location before the next request; tests must exercise injected clients as well as defaults.
- Bound binary download to 256 MiB, checksum file to 1 MiB, connect/header time to 10 s and total transfer to five minutes (including retries). Enforce streaming limit even without/misleading Content-Length. Test all installers/updater for bad redirects, TLS, oversized/slow/truncated data/checksum mismatch and leave old binary/config/DB intact. ## Migration, recovery, and limits

Never run real migration during this task or automated test. In the breaking release, old/unknown encrypted DB detection occurs non-destructively before normal migrations, WAL configuration, chmod or key loading. Error explains the supported process: retain old binary/version, config, DB with coherent WAL/SHM backup and master key; use the old release to export documented `warden-data` version 1; select **fresh storage**, run new init/recovery saved confirmation; start locked, authenticate/unlock, import into an empty managed dataset, verify counts/IDs/timestamps/references/notes/archive flags and usable secrets, then choose cutover. Never reuse the old DB path or automatically retire rollback artifacts. Failed/partial import rolls back managed records, not auth identity, and permits retry. Keep a deliberately nonempty destination unchanged. Tests use synthetic old-format DB fixtures and synthetic secrets only.

**Scope-excluded audit findings (owner decision):** external DB connections have no explicit verified TLS contract, and HTTP CONNECT can send Basic credentials over plaintext. These findings are not fixed by this plan. A direct plaintext DB/proxy leg can expose credentials/data to network observers or tampering; SSH protects only its encrypted segment, not an onward plaintext leg beyond the SSH endpoint. The owner explicitly limits this TLS work to Warden-owned boundaries and preserves external transport behavior. Record these as out-of-scope residual risks, not resolved findings or an end-to-end confidentiality claim. No conditional plaintext exception or new optional external TLS feature is planned.

Exports/recovery keys are plaintext offline secrets: warn before download, avoid sync/shared folders, revoke object URLs and avoid logs, retain only deliberately protected backups. Deleting current wrappers/credentials does not revoke copies of old backups; old recovery keys/passkeys can still decrypt snapshots that retain their wrappers. Passkey/credential revocation does not retroactively retract already returned data, pooled SSH graphs, remote sessions, or an exfiltrated DEK. Credential rotation at remote systems is necessary after exposure; DEK re-encryption/revoking historical backups is not promised by wrapper deletion. CLI API tokens are memory-only in the per-user agent but intentionally have no automatic expiry/rotation: an exfiltrated token remains valid until explicit server revocation or recovery/installation invalidation, including after agent exit. Disk IPC trust/discovery credentials are separate from API tokens.

An unlocked live server, malicious same-origin JS/XSS, a compromised browser/provider/OS, service account or trusted proxy can steal live keys/secrets. Go/JS clearing and dropping references is best effort, not proof of GC copies/strings/crypto internals being erased; disable core dumps/swap exposure where practical. Auth metadata/profile metadata are not all encrypted. Loss of every usable passkey and the recovery key means loss of vault access; no administrative encryption bypass. This design improves boundaries, not immunity to live compromise.

## Standards/API evidence and unresolved decisions

Standards checked for this design: [WebAuthn Level 3 PRF extension](https://www.w3.org/TR/webauthn-3/#prf-extension) (optional support, client outputs, registration may lack results), [Web Crypto AES-GCM/HKDF](https://www.w3.org/TR/WebCryptoAPI/) (KDF parameters, authenticated additional data and tag), and [TLS 1.3, RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.txt) sections 1/2/4/5 (authenticated confidential stream; application payload after handshake, no early-data assumption). Use these protocols, not provider-specific assumptions.

Parent's Context7 evidence `/go-webauthn/webauthn`, `ctx7:docs:752087b042ac2f5c2437a538`, describes challenge, origin/RP ID, required UV, expiry (explicit enforce configuration), credential ownership/user handles and extension handling. It is not evidence that PRF output itself is a signed authentication assertion. Before implementation imports/configures/calls any third-party API, retrieve Context7 for the exact selected version and inspect its current source, including expiry enforcement, serialization omitting PRF results, counter semantics and registration-follow-up verification. Do the same for SQLite transaction/open behavior, winio/Windows ACL APIs, SFTP exclusive mode, SSH cancellation and existing MySQL connection/channel lifecycle behavior. Missing API evidence is an implementation research task, not permission to guess or a vendor compatibility gate.
